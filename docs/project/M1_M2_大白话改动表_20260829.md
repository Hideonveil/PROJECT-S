# M1 / M2 大白话改动表

> 日期：2026-08-29  
> 当前状态：代码和测试已完成，本地提交 `df0670a`，尚未推送或部署 Production。

| 部分 | 之前是什么样 | 这次新增或修改了什么 | 有什么作用 | 如果不改会发生什么 |
| --- | --- | --- | --- | --- |
| M1｜手机尺寸基线 | 只知道手机端暂时被挡住，没有完整记录不同手机宽度下页面是否溢出。 | 加入 360、375、390、412、430 五档手机尺寸自动检查。 | 以后做手机版时，每次修改都能知道哪些尺寸被改坏。 | 很可能在一台手机看着正常，换一台就横向溢出、内容被截断。 |
| M1｜手机版当前状态 | 容易把“手机拦截页能显示”误认为“手机版已经做好”。 | 明确记录：现在仍是 PC-only Gate，真正手机版要从 M3 开始。 | 防止验收口径混乱，也防止提前对外宣称手机版可用。 | 后续可能拿一个拦截页当成手机版 PASS，真正功能没人测试。 |
| M1｜桌面防回归 | 主要检查常见桌面尺寸，缩放后的布局边界不清楚。 | 保留窄桌面检查，并加入 125% 缩放对应的等效 CSS 视口检查。 | 做手机版 CSS 时，不容易顺手把桌面端改坏。 | 手机样式可能误伤电脑端，出现按钮挤压、页面横向滚动。 |
| M1｜后续验收路线 | 手机端要测什么散落在讨论里。 | 写清 M3、M4、M5、M7 分别要替换和增加哪些测试。 | 后续开发有固定路线，不会每次临时决定。 | 容易漏掉键盘遮挡、聊天滚动、断线恢复、微信浏览器等问题。 |
| M2｜游戏资料总目录 | 游戏名称、段位、位置、人数和页面步骤分散写在网页、后端和 Runner 中。 | 建立服务端统一 `GameDefinition` 游戏目录。 | 一款游戏只登记一次，其他地方统一读取。 | 新增三款游戏时要改很多文件，漏一个地方就会出现规则不一致。 |
| M2｜公开目录接口 | 网页没有一份安全、统一的游戏资料来源。 | `/api/config` 返回经过裁剪的公开游戏目录。 | 网页和 Runner 能读取必要资料，但拿不到服务端规则函数或秘密。 | 要么继续硬编码，要么把不该公开的内部实现一起发给浏览器。 |
| M2｜首页配置步骤 | 首页流程仍带有 Deadlock 专属假设。 | 游戏目录决定 Ranked / Casual 要显示哪些步骤。 | 未来无畏契约、王者、三角洲可以有各自步骤，不用复制整个首页。 | 新游戏可能被迫显示 Deadlock 的段位、位置或错误步骤。 |
| M2｜段位提交 | 页面曾把中文展示名当作后端段位值；Deadlock 有兼容别名所以不明显。 | 页面显示中文，但提交稳定的 `rank.code`。 | 展示文案可以改，匹配规则仍收到稳定代码。 | 新游戏若没有中文别名，会出现用户选了段位却无法进入匹配池。 |
| M2｜段位和位置显示 | 浏览器还有一份 Deadlock 段位中文表和固定位置名称。 | Landing、Home、Matching、Room 都从游戏目录解析名称。 | 每款游戏能正确显示自己的段位和位置。 | 新游戏可能直接显示 `bronze` 这类代码，或错误显示 Deadlock 的“主核/辅助”。 |
| M2｜游戏名称 | 部分页面各自判断或映射 Deadlock 名称。 | 首页、个人页、公开目录、Matching、Room、Session Preview 统一查 catalog。 | 改名或新增游戏时，各页面自动同步。 | 同一款游戏可能在不同页面出现不同名字。 |
| M2｜默认游戏 | 空状态会在游戏目录加载前偷偷假定当前游戏是 Deadlock。 | 空状态不再写死游戏；目录加载后再选择第一个可用游戏。 | 游戏上下线或调整顺序时，运行状态不会被旧默认值污染。 | 新游戏成为主游戏后，用户仍可能被送进 Deadlock 配置或错误匹配池。 |
| M2｜匹配大厅 | 公开等待列表过去围绕 Deadlock 查询。 | 只展示 catalog 中当前开放的游戏；用户有有效 ticket 时按该游戏收窄。 | 多款游戏同时开放后，匹配大厅能正确区分游戏。 | 不同游戏用户可能混在一起，或新游戏玩家根本不显示。 |
| M2｜Casual 默认规则 | 网页、单机 Runner、分布式 Runner 都各自写一份默认人数和招募模式。 | 浏览器和 Runner 只提交用户偏好，最终默认值和边界由服务器统一决定。 | Casual 业务规则只有一个负责人，不会三套实现互相漂移。 | 压测显示能跑，真实网页却可能使用另一套人数规则，产生难查的匹配 Bug。 |
| M2｜容量测试选游戏 | Runner 默认围绕 Deadlock 生成段位、位置和人数。 | Runner 从 `/api/config` 获取游戏目录，并支持明确的 `--game-id`。 | 以后可以对任意已登记游戏跑同一套测试。 | 新游戏压测可能仍在打 Deadlock，得到一个看似 PASS、实际无效的结果。 |
| M2｜新游戏贯穿测试 | 测试只替换显示名，没有证明新游戏 ID 真能贯穿系统。 | 使用 `fake-arena` 贯穿 Landing、Home、Profile、Matching、Room 和 Capacity。 | 能提前发现新增游戏时的隐藏 Deadlock 硬编码。 | 等真实新游戏接入后才发现某个页面或 Runner 根本不认识它。 |
| M2｜安全边界 | 如果直接把服务端完整游戏定义发给网页，可能公开内部规则。 | Public catalog 明确排除规则函数、容量内部场景和秘密。 | 网页只拿展示和合法输入所需内容。 | 内部匹配实现可能被无意暴露，也会让前端依赖不该依赖的东西。 |
| 验证 | 修改分散，容易只验证单个页面。 | 113 个测试文件、469 项测试、TypeScript、Production build 和关键浏览器流程全部通过。 | 证明这次整理没有破坏现有 Deadlock 主流程。 | 目录重构可能表面正常，实际在 Room、段位提交或 Runner 中留下断点。 |

## 一句话总结

M1 是先把手机版开发的“尺子”立好；M2 是把所有游戏共用的信息收进“一本说明书”。下一步 M3 才开始真正制作手机端页面外壳。
